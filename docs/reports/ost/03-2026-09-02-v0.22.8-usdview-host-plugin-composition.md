# Plugin View cannot compose a usdview host add-on with `--with`

- Date: 2026-09-02
- Version exercised: `ost 0.22.8` on local Windows x86_64
- Runtime: `cy2026` / `usd`, artifact
  `sha256:3a4e399351763a5ef55575e5341b28adabf1ffe6cf55a1d3cc315e19aba9dbff`
- Source base: `eadca3f` plus the in-progress OST Plugin View integration
- Occasion: completing the host-integration milestone with the existing
  `usdviewStageRunner` Python `PluginContainer` and native `StageSession`
  binding
- Status: repository workaround implemented and packaged; interactive Level 6
  evidence unavailable because this runtime does not contain usdview
- Ask target: a future OpenStrata release that models usdview host add-ons

## Summary

`ost plugin view` composes a primary plugin bundle and any `--with` bundles by
adding each bundle's `plugin/`, `lib/`, and `python/` roots to the launched
session. That mechanism is a good fit for the Stage Runner adapter at execution
time, but the adapter cannot be named as a `--with` input because it is a
usdview Python host extension rather than one of the five modeled bundle kinds.

The attempted command fails before runtime resolution:

```powershell
ost plugin view plugins/runnerSchema tests/fixtures/minimal.usda `
  --with plugins/usdviewStageRunner --json
```

```text
OPERATION_FAILED: no openstrata.plugin.yaml in
'plugins\usdviewStageRunner' (is this a plugin bundle? try `ost plugin new`)
```

Adding a manifest solely to satisfy `--with` would require falsely labeling
the adapter as `usd-fileformat`, `usd-asset-resolver`,
`usd-package-resolver`, `usd-exec`, or `usd-schema`. The adapter implements none
of those contracts. It adds menu commands and a Qt timer to usdview, then calls
the same native `stageRuntime::StageSession` used by the standalone host.

The repository workaround stages the adapter into the existing
`runnerSchema` bundle's conventional `python/` root. The schema
`plugInfo.json` includes the Python plugin's nested `plugInfo.json`, and a named
root build intent performs the staging:

```powershell
ost build --intent plugin-view
ost plugin view plugins/runnerSchema tests/fixtures/character_walk.usda
```

This keeps one runtime implementation and gives `ost plugin view` the bundle
shape it already knows how to activate. It also couples host-adapter delivery
to a schema bundle because OpenStrata has no independent host-add-on shape.

## What worked

The named build completed with the host MSVC environment and the pinned runtime
activated. It staged these relevant files beneath
`plugins/runnerSchema/python/usdviewStageRunner`:

- `__init__.py` and `controller.py`;
- `_usdviewStageRunner.pyd`;
- the Python plugin's `plugInfo.json`; and
- the codeless Runner schema resources used by the package at import time.

The first staging implementation used a `POST_BUILD` command on the native
module. An incremental named build did not execute that command when the module
was already up to date, and OpenStrata correctly warned that it could not
attribute the unchanged staged `.pyd` to prior root-build evidence. The final
implementation uses a dedicated `ALL` staging target that depends on the native
module, so every `plugin-view` build synchronizes the complete payload even
when no compilation is necessary.

The root test run exercised the corrected named intent:

```powershell
ost test --intent plugin-view --jobs 8 --progress plain
```

All 39 CTest tests passed. The new `usdviewStageRunner.ost_plugin_view` smoke
test registered the schema bundle root, resolved the included
`usdviewStageRunner` plugin, imported the staged native binding, advanced one
fixed step, stopped, and confirmed that the Stage root layer text was
unchanged. This covers the bundle composition and discardable-layer contract
without requiring a window system.

The work also exposed a pre-existing standalone-build defect: its CMake file
used `USD_STAGE_RUNNER_SCHEMA_INSTALL_DIR` from the repository root without a
bundle-local fallback. `ost plugin build plugins/runnerSchema` therefore failed
with `install FILES given no DESTINATION`. Giving the bundle a `share/...`
default fixed that repository issue, and the standalone bundle build then
completed.

Packaging succeeded without an unmanaged-output override:

```powershell
ost plugin package plugins/runnerSchema --json
```

It reported all 8 package-relevant outputs matched the root managed
`plugin-view` build and created a 17-file archive. The package manifest includes
the Python sources, native `.pyd`, both plugin metadata files, and schema
resources. Package-origin verification also passed:

```powershell
ost plugin test plugins/runnerSchema --from-package --up-to 5 --json
```

The result was 11 PASS, 4 SKIP, and 0 FAIL. The skips were the expected
codeless-library checks and the absent optional golden file; schema
registration and apply/flatten round-trip both passed from the extracted
package. Running the bundle smoke again inside that extracted package's
`ost plugin run` session also succeeded, proving that the nested Python plugin
registration and native binding were usable after packaging rather than only
from the source tree.

## What remained unverified

The selected artifact has a valid OpenUSD 26.08 Python runtime but does not
ship `usdview`. The direct host check therefore passed by skipping Level 6:

```powershell
ost plugin test-view plugins/runnerSchema `
  tests/fixtures/minimal.usda --json
```

```text
[SKIP] L6 usdview.launch: usdview not in the runtime
```

This is not evidence of an adapter failure. It does mean the `cy2026` / `usd`
selection is insufficient to prove the command advertised in the host
milestone. A runtime containing usdview, Qt, and a display is still required
for the interactive launch. Jolt must additionally be discoverable when
building if `character_walk.usda` or the obstructed
`third_person_camera.usda` fixture is expected to simulate rather than report
the shared unavailable-backend error.

## Upstream asks

1. Model a truthful bundle or component shape for Python usdview host add-ons.
   A `usdview-plugin`/host-plugin kind, or an equivalent declared Python and
   plugin-metadata component, would let `--with` compose this adapter without
   pretending that it is a file format, resolver, Exec plugin, or schema.
2. Let that shape participate in `plugin build`, package activation,
   dependency composition, and `plugin view` while retaining Python ABI and
   native-extension provenance.
3. Consider making `plugin view` selection capability-aware. If a profile does
   not promise usdview, an explicit host-capability selector or preflight would
   make the difference between an OpenUSD Python runtime and a view-capable
   runtime visible before Level 6.

Until such a shape exists, co-locating the adapter payload with
`runnerSchema` is the narrowest working integration. The workaround is
deployment-only: simulation, timing, synchronization, and discard behavior
remain in the same shared libraries used by `stage_runner` and ordinary
usdview.
