# A local Windows build finishes work but does not return

- Date: 2026-08-30
- Version exercised: `ost 0.22.8` on local Windows x86_64, while the repository's
  generated CI bootstrap remains pinned to `0.22.6`
- Occasion: adding the first `physicsCore` contract slice in
  [`usd-stage-runner` PR #4](https://github.com/animu-sphere/usd-stage-runner/pull/4)
- Source commit: `aafe1d38565492ea99205821df1974d6007f8764`
- Status: local-only reproduction; root cause unknown
- Ask target: `ost 0.23.0`

## TL;DR

On this workstation, `ost build` configured the workspace, launched
`cmake --build`, and then kept reporting the child as running after build output
stopped. At 120 seconds of silence the supervisor changed the status to
`stalled`, but its configured two-hour timeout still had 7,079 seconds left.
The build log ended with a successful final link and repeated
`ninja: no work to do.` messages. The command was still alive at 255 seconds and
was interrupted manually.

The wait reproduced through `ost library build libs\physicsCore`, while building
its `runtimeCore` prerequisite, and through a direct developer-environment
`cmake --build ... --target physics_core_tests`. The direct reproduction means
this report does **not** establish that OpenStrata owns the underlying hang. It
does establish a dogfooding gap: once a child stops making progress, the `ost`
status stream names only the `cmake --build` wrapper and does not preserve enough
leaf-process evidence to distinguish a Ninja, compiler, pipe, handle, or SDK
problem.

Both Windows checks passed on the same commit:

- plain CMake `core (windows-2022)`;
- OpenStrata `workspace-pr-windows`.

The Ubuntu check passed too, and a separate clean WSL/GCC build ran all five
backend-neutral tests successfully. The finding is therefore scoped to this
local Windows toolchain combination, not to the source change or the published
runtime in general.

## 2. What `ost build` did

The workspace configure completed normally:

```console
$ ost build
msvc env    ...\VC\Auxiliary\Build\vcvars64.bat (43 vars)
runtime env openstrata-cy2026-windows-x86_64-py313-usd (5 vars)
...
-- inputSdl: backend none
-- stage_runner: OpenUSD support enabled (usd)
-- Configuring done
-- Generating done
```

OpenStrata then launched this child with a 7,200-second timeout:

```text
cmake.exe --build build/cy2026-windows-x86_64-py313-usd --config Release
```

Its supervisor emitted a progress record every fifteen seconds. The meaningful
transitions were:

```text
elapsed_ms=120155 status=stalled silent_ms=120151 timeout_remaining_seconds=7079
elapsed_ms=240322 status=stalled silent_ms=240319 timeout_remaining_seconds=6959
elapsed_ms=255344 status=running
```

The build log itself had already reached:

```console
[8/8] Linking CXX executable apps\stage_runner\stage_runner.exe
-- Configuring done (0.1s)
-- Generating done (0.0s)
ninja: no work to do.
-- Configuring done (0.1s)
-- Generating done (0.0s)
ninja: no work to do.
```

At inspection time the surviving `cmake` process had accumulated approximately
`0.02` CPU seconds. No `cl.exe` process was visible. The log is reused across
invocations and contains older failed attempts as well as this tail, so those
older diagnostics are not attributed to this invocation.

The command was interrupted rather than waiting almost two hours for the outer
timeout. It therefore has no natural exit code to report.

## 3. The smaller reproductions

### 3.1 Per-library build

The documented isolated-library path reproduced the same shape:

```console
$ ost library build libs\physicsCore
== build prerequisite runtimeCore ==
==> loaded MSVC environment (43 vars) from ...\vcvars64.bat
==> [configure] cmake.exe -S ...\libs/runtimeCore -B ...
-- Configuring done
-- Generating done
==> [compile-link] cmake.exe --build ...\libs/runtimeCore\build\...
```

No further output arrived for more than a minute. During the wait,
`runtimeCore.lib`, `runtime_clock_tests.exe`, and
`runtime_registry_tests.exe` existed with current timestamps. `cmake.exe` and
`ninja.exe` remained resident with near-zero CPU, and no compiler process was
visible. This command was also interrupted manually.

This narrows the symptom below OpenUSD and `stage_runner`: the prerequisite is a
standard-library-only core target.

### 3.2 Direct CMake/Ninja build

The generated target was then invoked directly after entering the same MSVC
developer environment, without an `ost build` supervisor:

```console
cmd.exe /d /c "call <vcvars64.bat> && cmake --build \
  build\cy2026-windows-x86_64-py313-usd --target physics_core_tests"
```

That command also remained alive with `cmake.exe` and `ninja.exe` resident.
`descriptors.cpp.obj` and `physics_world.cpp.obj` were written, while the test
executable had not appeared when inspected. It was interrupted.

This is the strongest boundary in the report: **OpenStrata is not required to
reproduce the wait.** An OpenStrata fix should not be proposed for a Ninja or
local toolchain defect that has not been identified. What OpenStrata can own is
the evidence it captures when the tool it supervises stops progressing.

show this commit is buildable; it cannot explain what the local processes were
waiting for.

## 5. The single ask

**P1 — when a supervised build first becomes stalled, write a safe diagnostic
snapshot that identifies the leaf process and the wait boundary.**

The current progress record is useful for proving that silence continues, but
it repeats the outer `cmake --build` command. After four minutes it still did
not answer whether CMake was waiting for Ninja, Ninja was waiting for a compiler
or response file, or a completed child had left a pipe or handle open. That is
the difference between a report an upstream can act on and one that can only say
"it hung here."

At the first `running` to `stalled` transition, preserve a diagnostic file under
the target's existing log directory containing:

1. the supervisor and descendant process tree, with PID, parent PID, executable,
   command line, elapsed time, and CPU time;
2. the resolved CMake, generator, compiler, and SDK versions;
3. the build log path, last-write time, byte size, and a bounded tail; and
4. the timeout and silence thresholds in effect.

Print the diagnostic path in the status record. Do not dump the full environment
or command secrets by default. A user should be able to interrupt the build at
that point and still attach one bounded artifact containing the facts needed to
continue the investigation.

This ask does not require `ost` to kill the child early or to diagnose Ninja.
It asks the supervisor that already detects `stalled` to make that detection
actionable.

## 6. Follow-up conditions

A later report should replace the open diagnosis only after one of these is
measured:

- the same local toolchain exits naturally after a specific environment or tool
  change;
- the diagnostic snapshot identifies a leaf wait and reproduces it outside
  `ost`; or
- an OpenStrata change captures enough evidence to route the defect to the
  owning tool.

Until then, the accurate statement is narrow: local Windows builds can finish
observable work and remain alive, direct CMake can reproduce it, hosted Windows
builds are green, and the current stalled record does not explain the wait.
