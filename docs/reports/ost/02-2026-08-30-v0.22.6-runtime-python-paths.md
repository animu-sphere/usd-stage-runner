# The Windows runtime exports its producer's Python paths

- Date: 2026-08-30
- Version exercised: `ost 0.22.6` on GitHub `windows-2022`
- Runtime: `cy2026` / `usd`, artifact
  `sha256:ebb0c7da509ee14ada19ee5b461de6996aad0024b5c9640f12dde76912e849b5`
- Occasion: adding a combined OpenUSD and Jolt integration build to PR #7
- Status: reproduced in hosted CI; consumer-side workaround applied
- Ask target: the next republished Windows runtime

## Summary

The pulled runtime is runnable under `ost runtime validate`, but a direct CMake
consumer cannot call `find_package(pxr)` on a GitHub-hosted runner. Its exported
package contains absolute Python paths from the machine that produced it.

The defect has two layers:

1. `pxrConfig.cmake` supplies the producer's `Python3_EXECUTABLE`,
   `Python3_LIBRARY`, and `Python3_INCLUDE_DIR` before asking CMake for Python's
   Development component.
2. `cmake/pxrTargets.cmake` embeds the producer's Python include directory in
   the `INTERFACE_INCLUDE_DIRECTORIES` of imported OpenUSD targets.

The first layer is designed to be overridable by defining exactly those three
cache variables. `Python3_ROOT_DIR` alone is only a search hint and does not
replace values the package config has already defined. The second layer is
static exported-target text and cannot be overridden with a CMake cache
variable.

## Evidence

Four successive hosted runs stopped in the combined configure while the Jolt
build itself succeeded. Once dependency errors were made visible, CMake 3.31
reported:

```text
Could NOT find Python3 (missing: Development Development.Module
Development.Embed) (found version "3.13.15")
  .../pxrConfig.cmake:48 (find_dependency)
```

The runner's `actions/setup-python` installation was
`C:/hostedtoolcache/windows/Python/3.13.15/x64`; the runtime config instead
names a producer-local `C:/Users/.../Python313` installation. The same runtime
also records that producer include directory in `pxrTargets.cmake`, so fixing
only dependency discovery would move the failure to CMake generation.

This agrees with the independently recorded `usd-vrm-plugins` OST runtime-path
report and its installed-package consumer workaround.

## Repository workaround

The hand-maintained combined CI path now:

- derives and verifies the executable, versioned import library, and include
  directory from the Python 3.13 installation selected by
  `actions/setup-python`;
- reads the baked include path from `pxrConfig.cmake`, then replaces that exact
  absent path in the materialized copy of `pxrTargets.cmake`; and
- runs the combined OpenUSD/Jolt build through `ost build`, whose generated
  toolchain supplies the host Python dependency values, with the pinned Jolt
  prefix added to `CMAKE_PREFIX_PATH`.

The immutable artifact is not modified. `ost runtime pull --force` restores the
materialized runtime byte-for-byte, and the workflow never publishes it.

## Ask

Republish the runtime with relocatable Python dependency metadata. The package
config should let `FindPython3` resolve the consuming host, and imported OpenUSD
targets should not contain an absolute include directory from the producer.
Until both are fixed, every direct CMake consumer must independently carry the
same repair.
